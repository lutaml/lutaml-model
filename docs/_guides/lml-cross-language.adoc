= Cross-language models with LML

LML (LutaML Model Language) is the opt-in boundary between a model declaration
and target-specific code. A Ruby exporter can describe attributes and format
mappings as neutral data. A consumer in another language can validate that data
and materialize its own model and writers. The v2 contract and its Ruby,
TypeScript, Rust, and Rust/WASM implementations are present in the current issue
#1033 work branches. Those branches are still unmerged and unreleased; this is
not a claim about a published gem, npm package, or crate. See the
link:../_references/lml-contract[LML contract reference] for the wire format and
current limits.

== Start with Ruby

The existing Ruby v1 API still exports a supported `Serializable` model and
checks it against its current source class:

[source,ruby]
----
document = Lutaml::Model::Lml.export(Catalog::Item)
File.write("item.lml.json", document.to_json)
Lutaml::Model::Lml.verify(document)
----

`verify` remains a source-drift check; its existing v1 document and checksum
behavior are unchanged. For portable graphs, the additive v2 API exports a
closed bundle, imports it without the source constants, and can verify that the
materialized classes preserve the declarations:

[source,ruby]
----
bundle = Lutaml::Model::Lml.export_bundle([Catalog::Item])
classes = Lutaml::Model::Lml.import_bundle(bundle)
Lutaml::Model::Lml.verify_materialization(bundle)
----

Portable projection rejects floats and declarations that cannot be represented
faithfully. It does not coerce floats or change existing Ruby serializers.

== Consumer capabilities

|===
| Target | Available in current issue work | Limits

| Ruby
| v2 graph export, validated import/materialization, mapping compilation, and materialization round-trip verification.
| Trusted value-type bindings are supplied by the consumer. Unsupported behavior remains a named rejection.

| TypeScript
| Bundle validation and artifact generation with JSON and YAML key-value codecs; the package exposes `generate` with a `--check` option.
| The checked-in CLI output formats are JSON and YAML; this guide does not claim XML generation.

| Rust
| Bundle validation, generated model and JSON codec artifacts, manifest checks, and `generate` / `check` CLI commands.
| The current Rust artifact capability is JSON only. Corpus pins verify corpus identity; they do not run replay cases. Native XML is blocked on `moxml-rs` issue #2.

| Rust/WASM
| Generated model and JSON codec bindings are available through the Rust WASM path.
| Keep target behavior in the generated consumer. This does not provide a cross-language runtime interpreter.
|===

Generated files contain declarations and codecs, not Ruby method bodies or
callbacks. Custom constructors, Proc defaults, imperative element-order
behavior, and custom serialization code remain handwritten and produce named
rejections when the portable contract cannot represent them faithfully.

== Verify generated artifacts

Ruby's artifact verifier checks the caller-pinned manifest and its files. From
the `lutaml-model` checkout, run:

[source,shell]
----
ruby scripts/lml/verify_artifacts.rb --manifest generated/manifest.json \
  --expected-sha256 sha256:EXPECTED_DIGEST --root generated
----

The TypeScript CLI is built from the standalone package (`npm run build`, Node
22 or newer); its shipped command shape is:

[source,shell]
----
node dist/cli.js generate bundle.json --out generated --format json --format yaml
node dist/cli.js generate bundle.json --out generated --format json --check
----

`--check` exits nonzero when generated files are missing or stale. Optional
`--bindings FILE` supplies trusted value-type bindings. The CLI accepts JSON or
YAML bundles and generates JSON and/or YAML codecs; it does not provide an XML
format option.

The Rust CLI is run from the Rust package checkout. It accepts JSON or YAML
bundles and emits JSON artifacts:

[source,shell]
----
cargo run --locked -- generate --input bundle.json --output generated
cargo run --locked -- check --input bundle.json --output generated \
  --manifest-sha256 sha256:EXPECTED_DIGEST
----

Optional `--corpus-index FILE --corpus-sha256 sha256:DIGEST` arguments must be
supplied together. They pin and validate corpus identity in the manifest; they
do not execute the corpus. The Rust artifact checker requires the caller's
manifest digest.

== Keep behavior in the target package

LML contains data, not Ruby method bodies or callbacks. A static PARG binding API
can associate grammar rule and capture names with a stable LML class ID during
trusted compile-time generation. It is not a runtime grammar interpreter and
does not embed executable code in the LML document. A Ruby consumer may prepend
an external handwritten behavior module to a class produced by
`Schema::ClassLoader`; that module remains consumer-owned and outside the
generated artifact.

Each standalone consumer package owns its dependencies, manifest, corpus pins,
and CI. This permits package relocation without changing LML IDs or making the
core repository a runtime dependency.
