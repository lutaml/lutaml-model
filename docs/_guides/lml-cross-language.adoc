= Cross-language models with LML

LML (LutaML Model Language) is the opt-in boundary between a model declaration
and target-specific code. A Ruby exporter can describe attributes and format
mappings as neutral data. A consumer in another language can validate that data
and materialize its own model and writers. The contract is effective now; v2
bundle import, reconstruction, generators, and CLI commands are still landing.
See the link:../_references/lml-contract[LML contract reference] for the exact
wire format and current capability status.

== Start with the current Ruby projection

The Ruby v1 API exports a supported `Serializable` model and verifies it against
the current source class:

[source,ruby]
----
document = Lutaml::Model::Lml.export(Catalog::Item)
File.write("item.lml.json", document.to_json)
Lutaml::Model::Lml.verify(document)
----

`verify` is a source-drift check: it resolves the Ruby class named by the
document, exports that class again, and compares canonical declarations. It does
not build a replacement class. This v1 API does not yet export a portable v2
graph bundle.

== Planned portable workflow

The v2 workflow is opt-in and validates a complete dependency graph before
building target classes. Model IDs combine the portable model identity with its
effective register. References, nested models, value types, and discriminator
cases resolve by ID, so a target may choose different local class names.

The intended consumer sequence is:

. Export roots and their graph into a versioned LML bundle.
. Validate document versions, IDs, references, defaults, capabilities, and
  checksums.
. Verify the pinned manifest, generator, source, corpus, dependencies, and file
  hashes before loading artifacts.
. Materialize classes using trusted target bindings, then apply mappings.
. Run the pinned replay cases and report expected/executed IDs and counts.

The Ruby bundle exporter/importer, standalone TypeScript and Rust package
commands, artifact verification command, and CLI syntax are **PENDING**. The
contract names the operations, but their invocation syntax is not shipped. Do
not copy a pending command into a build or release script as if it were usable.

== Versions and target capabilities

|===
| Contract surface | Version and opt-in boundary | Availability at base `8a8ef040`

| Existing Ruby export
| v1 document; existing checksum rules
| Available as `Lutaml::Model::Lml.export` and `.verify`.

| Portable document
| v2 model documents in a v1 bundle; explicit opt-in exact codecs
| Contract effective; bundle producer/validator pending.

| Artifact
| Manifest v1, schema v2, pinned generator, target, capability and file digests
| Verifier and consumer loading pending.

| Ruby generation/reconstruction
| Validate, materialize, then apply mappings
| Pending; current `verify` only checks for source drift.

| TypeScript / Rust / WASM
| Same stable model IDs and semantic source/corpus pins; target-specific bytes
| Generators and consumer packages pending at this base.

| CLI
| Import, export, and compile operations
| Pending; no stable command syntax yet.
|===

Capabilities are declared as a sorted unique list. A consumer must reject a
missing required capability with `capability_missing`; it must not silently
ignore a mapping or type it cannot implement. Exact portable values use decimal
strings at cross-language boundaries, preserving precision and authored lexical
form. Portable codecs are opt-in and do not change existing Ruby serializers.

== Keep behavior in the target package

LML contains data, not Ruby method bodies or callbacks. Custom constructors,
Proc defaults, imperative element-order behavior, and custom serialization code
remain handwritten and produce named rejections when they cannot be represented
faithfully. Generated files contain the model and mapping declarations only;
the target application owns writers and behavior.

A compile-time PARG binding hook can associate a grammar rule with a stable LML
class ID for coradoc M2. Keep the binding outside the LML document so the same
schema can be consumed in Ruby, TypeScript, Rust, or WASM. A Ruby consumer may
prepend an external handwritten behavior module to a class produced by
`Schema::ClassLoader`; the module remains consumer-owned and is not folded into
the generated artifact. The hook and command/API details are **PENDING** until
they land.

Keep each consumer package standalone, with its own manifest, dependency pins,
replay corpus index, and CI. This permits future package relocation without
changing LML IDs or making the core repository a runtime dependency.
